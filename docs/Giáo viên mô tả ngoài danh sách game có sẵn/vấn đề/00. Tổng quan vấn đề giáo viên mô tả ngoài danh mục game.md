# Đặt Vấn Đề: Giáo Viên Nhập Mô Tả Nằm Ngoài Danh Sách Game Có Sẵn

> **Kiến trúc CPF (Vấn đề cốt lõi)**: [[Mô tả ngoài danh mục game]] | [[Giải pháp cho vấn đề nếu như giáo viên gửi mô tả nằm ngoài cơ chế game hiện có|Giải pháp kỹ thuật tổng thể CPF]]

---

## 1. Bản Chất Thách Thức Kỹ Thuật

Khi giáo viên đưa vào một câu mô tả nằm ngoài danh mục 10 thể loại game có sẵn (ví dụ: *"Game đua xe vượt chướng ngại vật"*, *"Game bắn súng góc nhìn thứ nhất"*, *"Game nuôi thú ảo"*), hệ thống phải giải quyết bài toán: **Làm thế nào để hỗ trợ sự sáng tạo của giáo viên nhưng vẫn đảm bảo game chạy an toàn, mượt mà và đúng chuẩn mực sư phạm?**

Nếu để LLM tự do sinh mã HTML/JS không kiểm soát, hệ thống sẽ sụp đổ vì hai lỗi nghiêm trọng:
1. **Hallucinated Logic (Ảo giác mã nguồn)**: Tự bịa ra hàm/thư viện không tồn tại $\to$ Runtime Crash $100\%$.
2. **Vacuous Satisfaction (Thỏa mãn giả tạo)**: Sinh giao diện rỗng hoặc biến thành bài trắc nghiệm nhàm chán.

---

## 2. Hệ Thống 8 Giải Pháp Chiến Lược

1. **Thiết kế trước, viết code sau (GDD-First)**: Sinh Game Design Document (JSON) trước khi sinh code để kiểm tra bằng luật trong mili-giây. Áp dụng nguyên lý *Tích hợp nội tại* (Hành động chơi chính là hành động học).
2. **Ngân hàng mẫu cơ chế (Pattern Bank)**: Thu thập các công thức game đã được chứng minh, dùng kỹ thuật RAG để gợi ý và biến tấu bối cảnh thay vì sinh từ con số không.
3. **Hồ sơ độ tuổi kiểm tra được bằng máy (Age Profiles)**: Biến trực giác sư phạm thành file cấu hình chính sách (Mầm non: nút $\ge 64\text{px}$, không áp lực thời gian, có giọng đọc).
4. **Nội dung kiểm chứng độc lập**: Dùng code tiền định tính toán lại $100\%$ các bài toán số học, dùng mô hình thứ hai độc lập để rà soát kiến thức mở.
5. **Kỹ thuật hấp dẫn lành mạnh (Juiciness & Game Feel)**: Phản hồi tức thì ($\le 200\text{ms}$), hoạt họa nảy nhẹ, âm thanh dễ chịu, phiên chơi ngắn $3$–$5$ phút, bài trừ triệt để Dark Patterns.
6. **Quy trình sinh nhiều bước & Vòng sửa lỗi**: Đường ống phân rã: Schema cưỡng bức $\to$ GDD Planning $\to$ Kit Assembly $\to$ Best-of-N $\to$ Targeted Repair Loop.
7. **Bốn Cổng Kiểm Soát Chất Lượng (Quality Gates)**:
   - *Cổng 1 (Nội dung)*: Đúng đáp án, đúng ngữ pháp, an toàn sư phạm.
   - *Cổng 2 (Lứa tuổi)*: Ràng buộc tâm sinh lý theo hồ sơ cấp học.
   - *Cổng 3 (Kỹ thuật & Đồ họa)*: Chạy thử trên Headless Browser Playwright.
   - *Cổng 4 (Giáo viên duyệt)*: Xem trước trong Sandbox Iframe trước khi xuất bản.
8. **Đánh giá Đa tầng Thực nghiệm**: Kết hợp kiểm thử tự động, VLM chấm điểm bố cục, và giáo viên tiểu học đánh giá thực tế.

---

## 3. Tiêu Chí Lựa Chọn Mô Hình LLM Theo Từng Khâu

Không nên dùng một mô hình duy nhất cho toàn bộ hệ thống. Nguyên tắc kỹ nghệ: *Tác vụ dễ và lặp lại nhiều thì dùng model nhỏ/rẻ; tác vụ suy luận phức tạp quyết định chất lượng thì dùng model mạnh*.

| Bước Xử lý trong Pipeline | Năng lực Cốt lõi Cần ở Model | Cấp Độ Model Khuyến nghị |
| :--- | :--- | :---: |
| **Trích xuất Yêu cầu** | Tốc độ nhanh, chi phí rẻ, hiểu tiếng Việt tốt | Model nhỏ / Nhanh (Flash / Mini) |
| **Lập Kế hoạch GDD** | Khả năng suy luận sư phạm, tuân thủ Schema JSON | Model cấp Trung đến Lớn |
| **Sinh Code Sandbox Mới**| Viết code HTML5/Canvas chuẩn, tuân thủ ràng buộc dài | Model lớn nhất trong ngân sách |
| **Sinh DSL 10 Game Sẵn** | Điền đúng trường dữ liệu theo JSON Schema | Model cấp Trung là đủ |
| **Kiểm chứng Độc lập** | Độc lập, không bị lây nhiễm thiên kiến của model sinh | Model khác họ, cấp Trung |
| **VLM Chấm Đồ họa** | Năng lực thị giác (Vision), phát hiện tràn chữ/lệch layout | Model đa phương thức (Multimodal) |
| **Vòng Sửa Lỗi (Repair)**| Sửa chính xác theo chỉ mục lỗi, giữ nguyên phần còn lại | Model cấp Trung đến Lớn |
